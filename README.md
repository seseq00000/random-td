# 랜덤 타워디펜스

스타크래프트 유즈맵 "랜덤 타워디펜스"를 참고한 웹 타워디펜스.
뽑기의 운을 조합·미션·도전으로 극복하는 운영이 핵심 재미다.

**적은 12시 방향 포탈 한 곳에서 나와 빙빙 돌며 중앙 코어로 좁혀든다.** 코어에 닿으면 라이프가 깎인다.
타워는 코어를 둘러싼 슬롯에 **자동으로** 배치된다 — 좌표를 찍지 않는다.

전체 설계는 [`docs/design.md`](docs/design.md) 에 있다.

## 실행

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # vitest (core/ 순수 로직)
npm run typecheck
```

### 폰에서 확인하기

모바일 우선 UI라 **실기기 확인이 필수**다. 같은 Wi-Fi면 LAN IP 로 충분하다:

```bash
npm run dev -- --host     # Network: http://192.168.x.x:5173/
```

외부망이면 터널을 쓴다. `vite.config.ts` 의 `allowedHosts` 에 `.trycloudflare.com` 이
열려 있다 (Vite 6 은 모르는 Host 헤더를 403 으로 막는다):

```bash
cloudflared tunnel --url http://localhost:5173
```

## 밸런싱 시뮬레이터

`core/` 가 렌더러·DOM 을 모르기 때문에 그대로 Node 에서 돌아간다.

```bash
npm run sim                      # 전 전략 비교 + 설계 주장 검증
npm run sim -- --runs=1000
npm run sim -- --strategy=full --diag   # 웨이브별 유효 출력 계수
npm run probe                    # 웨이브 구성·피버 검산 등 단발 진단
```

`data/` 의 밸런스 상수를 손대기 전에 **반드시 먼저 돌려서 현재 값을 재라.**
손으로 하는 추정은 3배 낙관적으로 나온다 (아래 참고).

## 아트 — 숲속 자경단

역할의 **기능**과 동물의 **생김새**를 1:1로 맞췄다. 고슴도치가 가시를 직선으로 쏘는 걸 보면
관통이라는 걸 안다 — 설명이 필요 없다.

| 역할 | 동물 | 40px 에서 읽히는 단서 |
|---|---|---|
| 단일 딜러 | 고양이 냥 | 뾰족한 삼각 귀 |
| 광역 | 곰 | 둥근 귀, 큰 몸집 |
| 장거리 | 올빼미 빼 | 큰 눈 + 부리 |
| 제어(슬로우) | 나무늘보 늘 | 처진 눈, 긴 팔 |
| 관통 | 고슴도치 도 | **등의 삼각 가시** |
| 버프 | 강아지 멍 | 늘어진 귀 |

**세 축을 분리했다: 역할 = 실루엣 / 동물 = 몸통색 / 티어 = 테두리 등급.**
겹치지 않아서 40px 에서도 셋 다 읽힌다.

유닛 이름은 기존 SF 이름에 티어별 애칭을 붙인다 — `절대영도 늘보경`, `빅뱅포 곰왕`, `종결자 냥신`.
**무시무시한 이름과 귀여운 애칭의 갭**이 이 게임의 톤이다.

티어 표기는 T1·T2 는 숫자, T3 부터 **레어 / 유니크 / 에픽 / 레전드 / 신화**.
필드 타워(40px)에는 "레전드"가 안 들어가므로 거기선 숫자 + 테두리 색을 쓰고,
등급명은 벤치 카드·미션·결과 화면 같은 텍스트 UI 에서 쓴다.

**이미지 파일이 0개다.** 동물 6개를 그리는 함수 + 티어 팔레트로 42종이 전부 나온다.

### 정보 UI

- **유닛 상세 시트** — 벤치 카드나 필드 타워 목록을 **탭**하면 열린다. 공격력·공속·DPS 를 뭉치지 않고
  따로 보여주고, 역할별 특수 효과를 수치로 푼다 (슬로우 `속도 -35% · 1.5초`, 관통 `최대 3명`)
- **도감 + 역할 범례** — 7행(티어) × 6열(역할) = 42칸. **한 줄이 전부 밝아지면 그게 다이소 미션 달성**이다.
  발견 기록은 localStorage 에 영구 누적된다
- **적 툴팁** — 새 UI 없이 웨이브 미리보기 칩에 타입 설명을 채웠다. 판단이 필요한 준비 페이즈에 바로 보인다
- **동심원 가이드 링** — 격자선을 지운 자리에 링을 넣었다. 링이 곧 **사거리를 읽는 눈금**이다 —
  사거리 6짜리는 원이 6번째 링까지 줄었을 때부터 쏜다. 화면은 단순해졌는데 정보량은 늘었다
- **스폰 포탈** — 12시 방향에 붉은 반원. 코어 쪽으로 열려 있어 **나오는 지점과 흘러가는 방향**이
  같이 읽힌다. 적이 한 곳에서 나오므로 표시가 없으면 화면이 안 읽힌다
- **크기** — 캔버스는 600px 인데 폰에서 ~390px 로 축소돼 표시된다(실제 0.65배). 그래서 타워·몬스터를
  25% 키웠다. **폰에서 안 보이면 없는 것과 같다** — 폭을 늘리는 것만으로는 4% 밖에 못 얻는다
- **뽑기 확률표** — 도감 시트 맨 위. 지금 웨이브의 등급별 확률(막대)과 구간 전체표를 같이 준다.
  전체표는 "몇 웨이브까지 버티면 레전드가 나오나"를 계획하는 데 쓴다. 수치는 `data/gachaTable.ts`
  를 직접 읽는다 — 옮겨 적으면 두 곳이 어긋난다
- **상위 등급 축하 연출** — **레어(T3) 이상**을 뽑으면 동물 그림과 등급명이 뜬다.
  기준선을 등급명이 붙는 티어와 **같게** 맞췄다. T1·T2 까지 축하하면 초반 내내 팝업이 떠서
  "레어를 뽑았다"가 안 특별해진다. 전투 중에도 뽑을 수 있으므로 팝업은 **진행을 막지 않는다**
- **카드 아이콘** — 글자(냥/곰/빼…) 대신 진짜 동물 그림. `drawCreature` 결과를 data URL 로
  캐시해서 재렌더 비용을 없앴다 (종류가 유한해서 성립한다)

### 역할별 투사체

전부 같은 노란 동그라미였을 때는 **화면만 보고 무슨 유닛이 일하는지 알 수 없었다.**
"역할 = 동물 실루엣"이라는 규칙을 투사체까지 밀어붙였다.

| 역할 | 동물 | 투사체 | 왜 그 모양인가 |
|---|---|---|---|
| 단일 딜러 | 고양이 | **총알** | 공속이 가장 빨라 잔상이 촘촘하다 |
| 광역 | 곰 | **포탄** | 느리고 묵직하다. 착탄 파편이 제일 크다 |
| 장거리 | 올빼미 | **화살** | 길고 가늘어 화면을 가로지르는 선이 보인다 |
| 제어 | 나무늘보 | **고드름** | 반투명 얼음. 색이 슬로우 표시와 같다 |
| 관통 | 고슴도치 | **가시** | 아주 가는 바늘 — 여러 마리를 꿰는 게 보인다 |

**고드름 색(`#7fd8ff`)은 몬스터의 슬로우 링과 일부러 같다.** 파란 게 맞은 자리에 파란 링이
생기는 걸 보면 인과가 설명 없이 읽힌다. 꼬리와 착탄 파편도 투사체 색을 공유한다.

`core/` 는 안 건드렸다 — `Projectile` 에 `sourceDefId` 가 있어서 렌더러가 역할을 알아낼 수 있다.

### 타격감

전부 **렌더러 소유**다 — 파티클이 게임 결과에 영향을 주면 결정론이 깨지고 시뮬레이터가 무의미해진다.

| 이펙트 | 트리거 | 어떻게 알아내나 |
|---|---|---|
| 피격 흰 섬광 + 불꽃 | 적 HP 감소 | 렌더러가 **프레임 간 HP 차이**를 관찰 |
| 처치 파편 (몬스터 색) | 적 소멸 | 직전 프레임 위치·타입을 기억해뒀다가 터뜨린다 |
| 발사 섬광 | 타워 쿨다운 상승 | 쿨다운이 올라갔다 = 방금 쐈다 |
| 투사체 꼬리 | 매 프레임 | 직전 위치까지 선을 긋는다 |
| 화면 흔들림 | 코어 피격 | `coreFlash` 의 **상승 엣지**에서만 (매 프레임 걸면 계속 떨린다) |

**`Enemy` 에 `hitFlash` 필드를 넣지 않은 게 핵심이다.** 그게 편하지만, 한 번 허용하면
연출용 필드가 core 에 계속 쌓인다. 관찰로 복원할 수 있으면 관찰로 한다.

## 현재 상태 — 싱글플레이 완성

| 마일스톤 | 상태 |
|---|---|
| M1 코어 루프 — 격자·적 이동·배치·자동 공격·라이프 | ✅ |
| M2 뽑기·합성(+잠금)·슬롯 구매·판매 | ✅ |
| M3 미션·도전·적 4종·이중 스폰·30웨이브 | ✅ |
| M4 밸런싱 — 헤드리스 시뮬레이터로 설계 목표 달성 | ✅ |
| M5 닉네임 · 기록 · 랭킹 (localStorage) | ✅ |
| M6 나선 필드 전환 + 모바일 UI — 좌표 탭 폐지 | ✅ |
| 멀티 (독립 필드 경쟁) | 보류 — 설계는 `docs/design.md` 6장에 있다 |

### M6 — 왜 경로를 버리고 나선으로 갔나

폰에서 타일이 화면상 **20px 남짓**이라 배치 탭이 자주 빗나갔다. 좌표 변환은 멀쩡했고
반경 1타일 오탭 보정까지 넣어봤지만, 손가락이 뭉툭하다는 물리적 한계는 보정으로 못 덮는다.
그래서 **좌표 입력이라는 방식 자체를 없앴다**:

- 적은 경로를 걷지 않고 **바깥 원에서 나선으로 좁혀들어 중앙 코어**에 닿는다
- 타워는 코어를 둘러싼 슬롯에 **버튼 한 번으로 자동 배치**된다. 빈 칸이 없으면 "배치할 공간이 없다"
- 벤치 카드 상세는 호버가 아니라 **탭**, 회수는 우클릭이 아니라 **버튼** — 폰에서 못 쓰던 기능 둘을 살렸다

`core/` 가 적 위치를 `dist` 스칼라 하나 + `enemyPos()` 한 메서드 뒤에 숨겨둔 덕에
**`combat.ts` 는 한 줄도 안 바뀌었다.** 전투는 픽셀 거리만 보기 때문이다.

### 닉네임 · 기록

닉네임을 입력해 입장하면 판이 끝날 때마다 결과가 브라우저에 쌓인다.

- 저장 위치: `localStorage` (`random-td:records:v1`, 최대 200판)
- 순위 규칙: **도달 웨이브 → 잔여 라이프 → 미션 달성 수 → 먼저 기록한 쪽**
  설계의 멀티 순위 규칙과 같은 기준이라, 나중에 멀티를 붙여도 정렬 로직을 다시 만들 필요가 없다
- 랭킹은 **닉네임별 최고 기록**만 보여준다
- 저장소가 깨졌거나 용량이 찼거나 사생활 보호 모드여도 게임은 계속 돌아간다 (기록만 안 남는다)

`RecordStore` 인터페이스를 두고 `LocalRecordStore` / `MemoryRecordStore` 를 구현했다.
서버 랭킹으로 갈 때 구현체만 추가하면 UI 는 건드리지 않는다 — 그래서 API 가 처음부터 `Promise` 다.

### 화면 구성 — 모바일 우선

세로 한 화면에 고정된다. 스크롤되는 건 벤치(가로)와 시트(세로)뿐이고 본체는 절대 안 밀린다.

```
[♥ 20 라이프] [● 340 골드] [12 웨이브]  [준비 8초 ▶]  ← 상단 고정
──────────────────────────────────────────────
일반 ×14   물량 ×30   🔥 피버 ×4.8               ← 웨이브 미리보기
──────────────────────────────────────────────

            ( 나선 필드 )                         ← 정사각 캔버스

──────────────────────────────────────────────
 🎯미션  ⚡도전  🛡필드  📖도감  📜기록           ← 시트 탭
──────────────────────────────────────────────
[뽑기]  [냥×3][곰×1][빼×2][도×1]                ← 하단 독
 10G    [합성][배치][배치][배치]                    2행 그리드
        [멍×1][늘×3][ ⋯ ][ ⋯ ]                    8종류가 한 화면에
        [배치][합성][    ][    ]
```

**항상 보이는 건 라이프·골드·웨이브·뽑기·보유 유닛뿐이다.** 나머지는 전부 시트 뒤로 보냈다.
"다음 웨이브 시작"만 예외로 상단 페이즈 칩에 합쳤다 — 웨이브마다 누르는 버튼이라
시트에 넣으면 매번 두 번 탭해야 한다.

**벤치는 가로 스크롤 카드였다가 2행 그리드가 됐다.** 벤치를 종류 단위로 세면서 8장이
928px 가 됐는데 폰 화면은 390px 이라 3장밖에 안 보였다. 자동 합성을 끈 뒤로는
"빛나는 카드를 찾아 스크롤"해야 해서 합성이 번거로웠다.
세로를 더 쓰는 건 **공짜다** — 캔버스가 높이가 아니라 폭에 묶여 있기 때문이다.

타일에는 그림·등급·개수와 **버튼 하나만** 둔다. 지금 눌러야 할 게 무엇인지 타일이
스스로 정한다 — 합성 가능하면 금색 `합성`, 아니면 `배치`. 이름·DPS·팔기·잠금은
타일을 탭해서 여는 상세 시트가 맡는다. 빈 칸은 점선으로 남겨 "몇 종류까지 벌릴 수 있나"를 보여준다.

### 조작

| 조작 | 동작 |
|---|---|
| 닉네임 입력 → 시작 | 입장. 닉네임은 다음 방문에 자동으로 채워진다 |
| 뽑기 (10골드) | 랜덤 유닛 1개 → 벤치. **전투 중에도 된다.** 벤치가 **8종류**로 차면 막힌다 |
| 타일의 **배치** 버튼 | 빈 슬롯에 자동 배치. **자리는 고르지 않는다.** 없으면 "배치할 공간이 없다" |
| 타일의 **합성** 버튼 | 금색으로 맥동하는 타일에만 뜬다. 같은 종류 3개 → 상위 티어 랜덤 1종 |
| 타일 **탭** | 상세 시트 (공격력·공속·DPS·사거리·특수 효과 · 팔기 · 잠금) |
| 🔒 합성 잠그기 (상세 시트) | 그 종류는 3개가 쌓여도 합성되지 않는다 (컬렉터 미션용) |
| 상단 페이즈 칩 | 준비 페이즈 조기 종료 (남은 초 × 1골드) |
| 🛡 필드 시트 | 슬롯 구매(**전투 중에도 가능**) · 배치된 타워 목록 → **회수 / 팔기** |
| ⚡ 도전 시트 | 🔥 피버타임 · 💀 보스 소환 · 자동 합성 토글 |
| 🎯 미션 시트 | 진행 중인 미션과 달성 골드 |
| 📖 도감 시트 | **등급별 뽑기 확률표** + 동물 6종 역할 설명 + 42종 수집 현황 |

**뽑기·슬롯 구매는 전투 중에도 된다.** 원래는 "준비 = 결정, 전투 = 관전"이라는 리듬을 노리고
준비 페이즈 전용이었는데, 전투가 30~60초씩 이어지는 동안 아무것도 못 해서 답답했다.
**도전 선언만 여전히 준비 페이즈 전용**이다 — 웨이브 구성이 전투 시작 시점에 확정되므로
전투 중에 거는 건 애초에 성립하지 않는다.

**합성은 자동이 아니라 직접 누른다.** 합성할 수 있는 타일은 금색으로 맥동한다.
자동으로 합치면 "레어 3개를 모았다"는 순간을 못 보고 지나간다.

### 벤치는 개수가 아니라 **종류**로 센다

8칸 = **8종류**다. 같은 유닛은 몇 장이든 한 칸을 쓰고, 타일이 겹쳐 쌓인 모양 + `×3` 으로 보인다.

자동 합성을 끄자 중복이 계속 쌓여서 개수 기준 8칸이 금방 막혔고, "직접 합성한다"는 재미가
성립하지 않았다. 스택을 한 칸으로 세면 중복은 자유롭게 모으되 **"몇 종류까지 벌려둘 것인가"**
라는 판단은 그대로 남는다 — 컬렉터 미션의 기회비용도 살아 있다.

> 각성체는 같은 유닛이라도 별개 스택이다. 합성 재료가 아니라 별개 취급이기 때문.

> 캔버스에는 **어떤 입력 리스너도 없다.** 좌표를 찍을 일이 없으니 오탭이 구조적으로 불가능하고,
> 호버·우클릭에 의존하던 기능도 사라졌다.

### 확정 밸런스 (나선 전환 후 재튜닝, 시드 500개)

| 전략 | 평균 W | 중앙 W | 클리어 | 미션 골드 | 슬롯 | 설계 목표 | |
|---|---|---|---|---|---|---|---|
| 기본 경제만 (미션·도전 차단) | 18.8 | 22 | **0%** | 0 | 3.7 | W17~20 · 클리어 불가 | ✅ |
| 미션 방치 | 23.4 | 28 | 24% | 747 | 5.0 | — | |
| 미션 적극 | 24.6 | 30 | 44% | 2,027 | 5.5 | W24~27 | ✅ |
| 미션+도전 | 24.4 | 30 | **47%** | 2,746 | 6.4 | 클리어율 35~50% | ✅ |
| 도전 남발 | 21.9 | 29 | 40% | 2,474 | 6.1 | full 보다 나빠야 | ✅ |

설계의 핵심 주장 네 가지가 전부 실측으로 확인됐다:

1. **미션·도전 없이는 끝까지 못 간다** — 500판 중 클리어 0판
2. **미션이 격차를 메운다** — 0% → 44%
3. **도전이 추가로 기여한다** — 44% → 47%
4. **도전은 보드가 앞설 때만 이득** — 남발(40%)이 판단(47%)보다 7%p 낮다.
   "무조건 쓰는 게 이득"이 아니므로 선택이 살아 있다

> 3번의 여유는 3%p 로, 500판 표준오차(≈2.2%p)의 1.4배뿐이다. **방향은 맞지만 여유가 작다** —
> 도전 관련 상수를 건드리면 반드시 `--runs=500` 이상으로 다시 재라.
> 250판에서는 이 차이가 뒤집혀 보이기도 했다(45% vs 42%).
> 4번의 여유(7%p ≈ 3σ)는 그에 비해 단단하다.

### 유효 출력 계수는 웨이브 타입마다 다르다 (나선 전환 후 재측정)

`npm run sim -- --diag` 실측:

| 웨이브 타입 | 경로형 (구) | 나선 (현) |
|---|---|---|
| 물량(swarm) | 0.05~0.16 | 0.16~0.42 |
| 일반 / 장갑 | 0.12~0.27 | 0.28~0.74 |
| 보스 | 0.18~0.46 | 0.32~0.85 |

**나선으로 바꾸자 계수가 통째로 2~3배 뛰었다.** 경로형에서는 적이 타워 옆을 스쳐 지나갔지만,
나선에서는 적이 항상 중앙을 향해 들어오므로 사거리 안에 머무는 시간이 훨씬 길다.
같은 HP 커브를 두었더니 **기본 경제만으로 W28·클리어 28%** 가 나왔다(목표 W17~20·0%).

여전히 물량 계수가 가장 낮지만 전투 시간이 3~4배 길다.
**튜닝할 때 계수만 보지 마라 — `계수 × 전투 시간`이 실제 처치량을 결정한다.**

### 웨이브 구성

적은 **일반 · 장갑 · 물량 + 보스** 4종이다. 공중은 뺐다 —
"대공 유닛이 안 나오면 웨이브가 통째로 누출"되는 구조가 랜덤 뽑기 게임에서 너무 가혹했다.

| 웨이브 | 구성 |
|---|---|
| W1 / W3 | 일반 ×10 / 물량 ×30 (방어력 0, 수가 2.5배) |
| W7 | 장갑 (방어력 3배) — 방어력 개념을 여기서 처음 만난다 |
| 5의 배수 | 보스 ×1 (웨이브 HP 전체가 1마리에) |
| W21+ | 이중 스폰 — `일반 ×12 + 물량 ×10` 처럼 두 타입이 동시에 |

> 적이 3종이라 이중 스폰 조합은 3가지뿐이다. 후반이 반복적으로 느껴지면 새 타입을 추가한다.

### 밸런싱 이력

1. **M1 후** — 웨이브 HP 풀 상수를 실측으로 보정 (`900 × 1.38^(w-1)` → `300 × 1.355^(w-1)`).
   설계 문서의 `DPS × 시간` 추정은 실제 유효 출력의 약 3배로 낙관적이다 — 타워가 사거리 안에
   적이 있을 때만 쏘기 때문(uptime). `docs/design.md` 3.2절 "실측 보정" 참고.
2. **M2 후** — 판매 환급을 **티어 기준 → 실투입 골드 기준**으로 변경. 티어 기준이면 후반에
   10골드로 뽑은 T6 를 1,215골드에 파는 무한 골드 경로가 열린다 (프로브에서 뽑기 11,585회로 터졌다).
   각 유닛이 `paid` 를 들고 다니고 합성 결과가 재료 3개의 합을 물려받는다.
3. **M3 구현 중** — 피버타임이 HP 풀에만 배수를 적용하고 **마리수에는 적용하지 않던 버그**를 잡았다.
   개체 HP 가 0.82배로 내려가야 하는데 1.8배로 올라가서, "물량형 웨이브"라는 설계와 정반대로 동작했다.
4. **M4 (확정)** — 시뮬레이터로 재면서 `data/` 상수만 조정했다:

   | 상수 | 원안 → 확정 | 근거 |
   |---|---|---|
   | `WAVE_POOL_GROWTH` | 1.355 → **1.39** | 기본 경제만으로 75% 클리어하던 걸 0% 로 |
   | `DAISO_REWARDS` | 합 6,510 → **합 1,960** | 미션 골드가 설계 추정의 10배였다 |
   | `COLLECTOR_GROWTH` | 2.0 → **1.5** | T7 컬렉터 2,560골드가 후반 경제를 무너뜨렸다 |
   | `COLLECTOR_COUNT` | 5 → **4** | ⭐ 아래 참고 |
   | `FEVER` 배수 | 3.0 / 2.0 → **3.5 / 2.5** | 도전 6회가 클리어율을 8%p 밖에 못 바꿨다 |
   | `CHALLENGE_BOSS` 보상 | `150+25w` → **`200+45w`** | 위와 같음 |

   ⭐ **컬렉터 5개 → 4개가 결정적이었다.** M3 에서 "컬렉터 미션이 순손해"로 보였던 문제의
   원인은 보상이 작아서가 아니라 **비용이 커서**였다 — 벤치 8칸 중 5칸을 여러 웨이브 묶어두면
   그동안 합성이 멈춰 보드가 뒤처진다.

   **실패한 시도도 기록해둔다**: 배치를 순수 DPS 순으로 바꿨더니 클리어율이 57% → 30% 로 떨어졌다.
   DPS 가 낮은 제어·대공은 숫자에 안 잡히는 가치가 크다. **역할 다양성이 순수 화력보다 중요하다** —
   설계 주장이 반증 시도를 통해 확인됐다.
5. **공중 제거 후 (확정)** — 공중 적을 없애자 난이도가 크게 내려갔다(기본 경제만 W19.8/0% → W28.9/32%).
   "대공 없으면 전멸" 웨이브가 사라지고 저격 7종이 항상 유효해진 탓이다. 다시 잡은 것:

   | 상수 | 변경 | 근거 |
   |---|---|---|
   | `sniper.range` | 7 → **6** | 7 로 올렸더니 uptime 급등 — **사거리가 유효 출력의 지배 변수**다 |
   | `WAVE_POOL_BASE` | 300 → **900** | 초중반을 올려 약한 보드가 일찍 죽게 |
   | `WAVE_POOL_GROWTH` | 1.39 → **1.34** | 후반 절벽을 완화해 강한 보드는 완주하게 |
   | `SLOT_PRICES` | 총 1,450 → **총 4,520** | 아래 참고 |
   | `CHALLENGE_BOSS.hpMul` | 1.5 → **1.3** | 성공률이 낮아 도전이 항상 손해였다 |
   | `CHALLENGE_BOSS` 보상 | `200+45w` → **`250+60w`** | 위와 같음 |
   | `FEVER.bountyMul` | 3.5 → **4.0** | 위와 같음 |

   **슬롯 가격 3배가 결정적이었다.** 공중이 사라지자 모든 전략이 T7 에 도달해서(최고티어 6.9)
   티어가 실력 차를 못 만들고 **슬롯 수만 남았다**. 골드가 남아도 보드 상한에 막히니
   미션·도전이 결과를 못 바꿨다. 슬롯을 진짜 병목으로 만들자 스프레드가 되살아났다.

   **커브를 "더 가파르게"가 아니라 "모양을 바꿔서" 잡았다.** growth 만 올리면 후반이 절벽이 되어
   전 전략이 0% 가 된다. BASE 를 올리고 GROWTH 를 낮춰야 초중반은 어렵고 후반은 넘을 만해진다.
6. **나선 전환 후 (확정)** — 유효 출력 계수가 2~3배로 뛰어 전 구간이 쉬워졌다
   (기본 경제만 W28.2 / 클리어 28%). 잡은 것:

   | 상수 | 변경 | 근거 |
   |---|---|---|
   | `RADIUS_CURVE` | 신설 = **2** | ⭐ 아래 참고 |
   | `SPAWN_ANGLE` | 황금각 분산 → **12시 고정** | 어디서 나오는지가 안 읽혔다. 전체가 1.2웨이브 어려워졌다 |
   | `WAVE_POOL_BASE` | 900 → **1580** | 계수 상승분을 커브 전체로 흡수 (단일 스폰 후 재조정) |
   | `WAVE_POOL_GROWTH` | 1.34 → **1.3225** | 후반 절벽 방지 (BASE↑ + GROWTH↓) |
   | `CHALLENGE_BOSS.hpMul` | 1.3 → **1.2** | 도전이 골드를 더 벌고도 클리어율이 같았다 |
   | `CHALLENGE_BOSS` 보상 | `250+60w` → **`330+85w`** | 위와 같음 |
   | `FEVER.bountyMul` | 4.0 → **4.8** | 위와 같음 |

   **스폰 지점을 하나로 모으는 것도 밸런스 변경이다.** 원 전체에서 흩어져 나오던 걸 한 곳으로
   모으자 적이 나선 위에 한 줄로 늘어서면서 전 전략이 **약 1.2웨이브 어려워졌다**
   (기본 경제만 W18.8 → W17.5). 순수한 연출 변경처럼 보여도 반드시 다시 재야 한다.

   ⭐ **반경 곡선 지수가 결정적이었다.** 나선에서는 모든 타워가 코어 옆에 모이므로,
   반경이 등속으로 줄면 **사거리 3짜리와 6짜리가 거의 같은 시간을 쏜다**. 경로형에서
   "어디에 놓느냐"가 만들던 uptime 차이가 통째로 사라져서 전략 간 격차가 뭉개졌다
   (기본 28% vs 미션+도전 99%). 지수를 2로 두어 적이 여정의 절반을 반경 5.4타일 밖에서
   보내게 하자, 그 구간에 닿는 건 장사거리뿐이 되고 **보드가 넓을수록 커버 구간이 늘어난다** —
   스프레드가 되살아났다(기본 W19.2 / 미션+도전 W22.7).

   **HP 커브만으로는 못 잡는 문제였다.** BASE 를 올리면 W1 이 터지고, GROWTH 를 올리면
   후반이 절벽이 된다. 두 끝이 모두 묶여 있어서 "약한 보드는 일찍 죽고 강한 보드는 완주한다"를
   만들 수 없었다. 커브가 아니라 **유효 출력의 분포**를 건드려야 했다.

   **클리어율은 후반 커브에 극도로 민감하다.** `GROWTH` 를 1.310 → 1.317 로 0.007 올렸더니
   클리어율이 52% → 30% 로 떨어졌다. 다수의 판이 W29~30 경계에 몰려 있기 때문이다.
   후반을 건드릴 땐 **0.005 단위로** 움직여라.

## 구조

핵심 원칙: **`core/` 는 결정론적이고 렌더러·DOM 을 모른다.** RNG 는 시드를 주입받는다.
이 하나로 유닛 테스트, 리플레이, 헤드리스 밸런싱 시뮬레이터가 따라온다.

```
src/core/     순수 로직 (렌더/DOM 의존 없음) — 나선 기하 `orbit.ts`, 기록 도메인 `record.ts`
src/data/     밸런싱 수치 전용 — 코드 수정 없이 튜닝
src/storage/  기록 저장소 어댑터 (localStorage / 인메모리)
src/render/   Canvas 2D
src/ui/       DOM 오버레이
src/sim/      헤드리스 프로브 / 시뮬레이터
tests/        vitest — core/ 와 storage/ 대상
```

`core/orbit.ts` 가 경로형의 `core/path.ts` 를 대체한다. 진행도는 여전히 **`dist` 스칼라 하나**이고
(클수록 코어에 가깝다), 위치는 `orbitPosition(dist, angle0)` 이 극좌표로 만든다.
`targetPriority: 'first'` 의 "누출 직전을 먼저 막는다"는 의미가 그대로 보존된다.
